Bee CLI and Bee MCP server

1. Task: Answer "Did Daniel call?" from Bee data. Steps: Put each conversation's short_summary from bee conversations list into the agent's context. Expected: The model finds the call. Actual: Titles like "Family Care During Memory Decline" don't say who called; the model answered "I can't see that". Severity: Medium. Workaround: Include up to 700 characters of each conversation's full summary per turn (conversation_store.day_index) and a conversations tool that greps local transcripts by person. Suggestion: Return participants or named entities per conversation in conversations list, or add a --person filter.
2. Task: Have the companion speak as a participant in the recorded conversations. Steps: Feed Bee summaries to the agent. Expected: "You talked to your son Daniel." Actual: Summaries describe the wearer in the third person ("the man", "the father", "the husband"), and the model repeated that back to the user. Severity: Low. Workaround: A sentence in the opening message: "I took part in all of them; the summaries may call me the man, the father or the husband." Suggestion: A first-person summary option, or a speaker label that marks the wearer in transcripts and summaries.
3. Task: Keep a local copy of conversations current while one is still being recorded. Steps: Poll bee conversations list --limit 100 with cursors, compare updated_at and state to the local file. Expected: A --since filter or a change feed. Actual: The full list on every sync; in-progress conversations detected by hand from state not equal to COMPLETED. Severity: Low. Workaround: Sync at most once a minute on demand and every five minutes in the background; write an Updated line into each local file to compare. Suggestion: conversations list --since, and a webhook or long-poll for new and updated conversations.
4. Task: Show key takeaways and action items from a conversation on the Highlights page. Steps: Read summary from bee conversations list. Expected: Structured fields for takeaways and action items. Actual: They live inside free-form Markdown under headings whose wording varies. Severity: Low. Workaround: bee_data._section scans the Markdown for a heading containing "key take" or "action item" and collects the bullets under it. Suggestion: Expose key_takeaways and action_items as arrays in the conversation object.
5. Task: Render a conversation's transcript in order. Steps: Call bee conversations get with the id. Expected: One ordered transcript. Actual: get returns an unsorted transcriptions array, and bee conversations transcript returns a different, fuller shape; utterances needed sorting by spoken_at then start. Severity: Low. Workaround: Drop transcriptions from get, always use transcript, sort client-side. Suggestion: One canonical, ordered transcript shape.
6. Task: Ask the user before any tool that changes their Bee account. Steps: Inspect the tool specs the Bee MCP server exposes to Strands. Expected: A read-only or destructive hint per tool. Actual: No annotation we could use; write tools had to be inferred from names. Severity: Medium. Workaround: A regex in ConfirmWrites that matches tool names starting with bee_create, bee_update, bee_delete, bee_complete, bee_accept or bee_dismiss. Suggestion: Set MCP readOnlyHint and destructiveHint annotations on the Bee MCP tools, and surface them in the Strands MCPClient tool spec.

Strands Agents SDK

7. Task: Install a fixed, known-safe reply when a safety rule still fails after three rewrites. Steps: In steer_after_model, return Proceed and replace the message content. Expected: A documented steering action that substitutes the reply. Actual: Only Proceed and Guide exist; the replacement works because Strands reuses the same message object, which is not documented as supported. Severity: Medium. Workaround: Overwrite message["content"] in place with the fallback text. Suggestion: A Replace(text=...) steering action.
8. Task: Bound the number of corrections per turn so a stubborn model cannot loop. Steps: Look for a per-turn guide counter in the steering handler. Expected: The handler knows how many Guides it has issued this turn. Actual: Not available; BeeSteering keeps its own turn-to-count dictionary keyed by the session transcript length. Severity: Medium. Workaround: As above, with MAX_GUIDES_PER_TURN = 3 and MAX_TOOL_BLOCKS_PER_TURN = 6. Suggestion: Expose a per-turn guide count, or a max_guides option with a fallback callback, on SteeringHandler.
9. Task: In a steering handler, find the user message that started the current turn and the tool calls made since. Steps: Inspect agent.messages inside steer_after_model. Expected: The current turn's user text and tool calls available on the event. Actual: Steering Guide messages are appended as user turns, indistinguishable from real user turns, so they also confuse any code that counts exchanges. Severity: Medium. Workaround: Prefix every guide with "[steering] " and skip such messages in BeeSteering._turn and TopicOffloadManager._exchange_starts. Suggestion: Mark steering messages in message metadata, and pass the current turn's user text and tool calls into the steering callbacks.
10. Task: Keep long-term memory pinned at the top of the context while a custom ConversationManager trims old exchanges. Steps: Subclass ConversationManager, implement apply_management and reduce_context. Expected: A way to mark messages as pinned. Actual: The manager owns the whole list; the two seed messages had to be rebuilt and re-inserted on every trim, and removed_message_count maintained by hand. Severity: Low. Workaround: As above, with PINNED = 2. Suggestion: A pinned-messages concept on ConversationManager, or a hook to re-render the seed after trimming.
11. Task: Call model.structured_output for fact extraction from inside the agent's conversation manager and end-of-session code. Steps: Iterate the async structured_output stream. Expected: A synchronous helper for one-shot structured output. Actual: The call is async and may run inside the agent's running event loop, so asyncio.run fails; it had to be pushed to a worker thread. Severity: Medium. Workaround: memory._structured runs asyncio.run inside a ThreadPoolExecutor. Suggestion: A sync structured_output convenience, safe to call from hooks and conversation managers.
12. Task: Approve a write tool from a web page, not a terminal. Steps: Cancel or allow in a BeforeToolCallEvent hook. Expected: An async or deferred approval path. Actual: The hook is synchronous and must decide before returning, so the agent thread blocks until the browser answers. Severity: Medium. Workaround: server.py runs the agent on one worker thread; the hook waits on a threading.Event with a 600 second timeout while the page polls the job endpoint and posts Allow or Decline. Suggestion: A first-class human-in-the-loop approval state for tool calls (pause, then resume with the decision).
13. Task: Report token usage per chat message in the UI. Steps: Read usage in an AfterModelCallEvent hook. Expected: A usage field on the event. Actual: Found nested at event.stop_response.message metadata usage, undocumented for this purpose. Severity: Low. Workaround: TokenUsagePrinter and JobRecorder dig it out. Suggestion: Surface input_tokens and output_tokens directly on the event.
14. Task: Make tool calls from a small model validate against tool schemas. Steps: Attach tools and watch calls. Expected: Typed arguments. Actual: Small models send every argument as a string ("False", "100", "None") and the call fails validation. Severity: Medium. Workaround: CoerceToolArgs, a BeforeToolCallEvent hook, casts strings to the schema's boolean, integer or number types, drops "None", and clamps to minimum and maximum. Suggestion: An opt-in lenient coercion mode in the tool executor.

strands-decider 2B

15. Task: Run StrandsAgents/strands-decider-2B-hobson-v19 on a laptop GPU for the topic gate. Steps: load_engine with device set to cuda. Expected: It fits. Actual: 4 GB of VRAM is too small; fell back to CPU, where latency grows with input length. Severity: Medium. Workaround: Run on CPU; feed a gist of memory (8 words per item) and only the last 400 characters of the previous reply; regex short-circuits for small talk, safety and memory mentions so most messages skip the decider. Suggestion: A quantised or smaller checkpoint, and guidance on input length versus latency.
16. Task: Use the decider as a memory retriever: one yes/no question per stored topic in a single engine.ask call. Steps: Build a dictionary of NoulQuestions keyed topic_0 to topic_n, each with that topic's summary in its instructions. Expected: Clear guidance on how many questions per call and how long instructions may be. Actual: It works well, but we found no documented limits; we capped at the topics present and MAX_RECALLED = 2. Severity: Low. Workaround: Trial and error. Suggestion: Document question-count and instruction-length limits, and show the multi-question retrieval pattern in the README; it is a strong use of the model.

Amazon Bedrock

17. Task: Get Nova Micro to call remember for a lasting fact and keep its reasoning out of the reply. Steps: Instruction in the system prompt. Expected: A tool call and a clean reply. Actual: Often no call; sometimes "Tool call: remember {...}" printed as text; thinking tags leaked into the reply; a long system prompt was under-weighted once tools were attached. Severity: High for this use case. Workaround: Steering nudges once per turn; clean_reply strips thinking tags and "Tool call:" lines; long-term memory is delivered as a pinned user and assistant exchange rather than only in the system prompt; offloaded exchanges are rendered as notes ("I said" / "You replied") so the model does not copy a transcript format. Suggestion: Nova tool-use guidance for small models, and a server-side option to suppress inline reasoning in the final text.
18. Task: Try Claude Haiku on Bedrock as an alternative companion model. Steps: Set the model id to the global Claude Haiku 4.5 profile in BedrockModel. Expected: It runs with the same credentials as Nova. Actual: Access denied until the Anthropic use-case form is submitted in the Bedrock console, which is a surprise mid-hackathon. Severity: Low. Workaround: Stayed on Nova Micro; left the Claude line commented out in bee.py. Suggestion: Surface the use-case-form requirement in the model access error message, with a link.
19. Task: Pick a model id for Nova Micro that works from our region. Steps: Use apac.amazon.nova-micro-v1:0. Expected: A plain model id. Actual: Nova Micro is reached through a geographic inference profile (apac) that routes across regions, which matters for a health-adjacent app that may need to pin data residency. Severity: Low. Workaround: Documented that a clinical deployment must pin a single-region profile. Suggestion: Make the region routing of inference profiles explicit in the model list and in ListFoundationModels output.
